# 0028. A command-line client in the app's bundle, one engine at a time

**Decided.** Kuri has a second client: `kuri`, a command-line tool in the terminal. It ships inside the app, at `Kuri.app/Contents/Helpers/kuri`, and people put it on their `PATH` with a symlink. Like the app, it opens its own engine in-process (`Engine.open`) and follows `events()` ([decision 0001](0001-single-process-engine.md)). Launching Kuri from Finder starts the engine with the SwiftUI client; running `kuri` starts it with the terminal one. Both use the same `~/.config/kuri`: the same config, database and Keychain items.

- **One engine per home folder.** `Engine.open` takes an exclusive `flock` on `kuri.lock` in the home folder and fails with a readable error naming the process that holds it. You use the app or the CLI, not both at once. The kernel drops the lock when the process exits, so a crash leaves no stale lock. The lock file records the holder's process id, so each client, finding the other, offers to quit it: kuri asks the app to quit as you would, and the app, once you confirm, sends kuri SIGTERM.
- **The commands.** `kuri [prompt]` starts an interactive session with the current folder attached, read-write. `kuri -p <prompt>` runs one turn, streams the answer as text and exits with 0 (done), 1 (failed) or 130 (cancelled); piped stdin is added to the prompt. `-c` continues the latest conversation attached to this folder, and `-r [id]` picks one or opens it by id prefix. Options: `-m <provider/model>`, `--no-folder`, `--read-only`, `--add <path>`. Two subcommands: `kuri models` and `kuri sandbox setup|status`. Inside a session: `/model`, `/folders`, `/context` (what fills the context window, as the inspector shows it), `/shell <command>` (runs it in your own shell, in this folder, so a second terminal tab isn't needed), `/compact`, `/retry`, `/new`, `/clear`, `/exit`. Ctrl-C or Esc stops a turn, and Ctrl-D quits.
- **Only the app picks up waiting turns.** The CLI never calls `resumePendingTurns()`, so questions left open in the app aren't asked again in a terminal.
- **`-p` makes no titles.** It opens the engine with `titles: false`: it exits as its turn ends, and a title request would be cancelled anyway. Interactive sessions get titles as the app does.
- **`ask` tools in `-p`.** Approvals are asked on `/dev/tty` when there is one. Without a terminal they're denied, and the CLI says so. There's no flag to approve everything: policies live in `config.json`.
- **Keys are set up in the app.** The CLI only uses the providers already configured. It has no commands for keys or config: configuration is files ([decision 0006](0006-config-in-files.md)), and API keys are saved in Settings › Models.
- **Text output only.** No JSON output until something needs it. The CLI opens the engine with `blocks: []`, so the instructions describe no reply blocks ([decision 0026](0026-reply-blocks.md)).

**Why.** The engine was built to be a client-independent facade, and the CLI is the first client besides the app that proves it. Each client having its own engine needs nothing new between them: no protocol, no socket, no question of which client answers an approval. Nobody runs a terminal session and a window session on the same data at once, so the lock costs little. A separate helper rather than one binary for both keeps AppKit and SwiftUI out of the terminal process. `kuri` and `Kuri` can't both sit in `Contents/MacOS` on a case-insensitive volume.

**Cost.** The CLI can't start while the app is running, and the app can be running in the menu bar from login; the CLI then asks you to quit it. Each `kuri` run starts from cold: MCP servers are spawned again, so `-p` waits for them (with a timeout) before its turn, and the first `shell` call boots a VM (about half a second). The helper is signed on its own, with the virtualization entitlement, before the app. The Keychain items trust the app that saved them, so the CLI asks for access once, and again after each rebuild while builds are ad-hoc signed. Both binaries link the engine statically, so it's in the bundle twice: stripped, `kuri` is 25 MB of a 58 MB app. A shared KuriKit framework would halve that, but the hardened runtime's library validation only loads frameworks signed by the same team, and ad-hoc signatures have none, so neither binary would launch until releases are signed with a Developer ID. One executable for both, picking the client from the name it was started under, was set aside as a workaround. Sharing one engine between clients (the app hosting a local endpoint, the CLI connecting to it) would remove the cold starts and the lock, and is the same work as the network server for an iOS client; it waits until one of them is needed.
